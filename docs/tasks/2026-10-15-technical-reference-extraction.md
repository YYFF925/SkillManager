## 一、目标

根据 Skill Manager 的需求清单，系统检查旧项目中有哪些技术、数据、素材、实现经验和验证案例
能够帮助实现这些需求，提取到本项目自己的技术文档。

提取范围由需求及实际发现决定，不预先限定技术主题、源码目录或可复用方案。
现有技术参考只是一部分已有成果，不是本次提取的范围清单。
不要因为某个技术点不属于上一版任务单的七个方向，就跳过它。

主 Agent 需要回答：

- 为满足这些需求，哪些技术问题值得了解？
- 旧项目有没有相关实现，实际解决了什么问题？
- 哪些内容可以帮助新项目，适用前提和局限是什么？
- 哪些只是旧产品行为，提取时应当剥离？

完成的是技术参考提取与审查，不是产品开发，也不在本轮决定全部实现方案。

## 三、先梳理需求，再分配提取工作

### 1. 主 Agent 建立需求覆盖表

主 Agent 先完整阅读需求，整理出当前功能、跨功能约束及已知痛点。
按能理解和核查的需求单元组织，粒度由实际内容决定，不要求每段访谈各占一行。

覆盖表至少表达：

| 需求与依据 | 为实现它需了解的技术问题 | 源码检查线索 | 负责子代理 | 发现与交付状态 |
|---|---|---|---|---|

梳理时不要只看已出现的技术名词。
用户提出的“大库获取总失败”“不知道有哪些能力”“龙虾技能频繁修改”等使用问题，
也可能指向原任务主题之外有价值的技术参考。

覆盖表不是新的需求规格。重复讨论可合并，已被替代的结论应标清，不重新激活。

### 2. 据需求安排至少五个子代理

实际委派至少 **5 个不同子代理**，职责由主 Agent 根据覆盖表安排，不预设五组或七组固定主题。
可以按业务场景、关联需求或实际技术问题分工；某个问题需多个视角时也可协作检查。
发现新线索后允许调整职责、补查与增加子任务。

可根据可用并发分批执行，不要求同时运行五个进程；但不能用五个章节冒充五个子代理。
主 Agent 记录实际子代理标识／任务名、职责和交付。

每个子代理都需要阅读自己负责需求的上下文与共享约束。
只看一个标题就搜索同名文件，不算完成需求驱动的检查。

### 3. 沿实际调用链检查

从相关用户动作、结果或数据出发追踪实现，可跨越前端、核心服务、CLI、文件读写、配置、
外部工具调用、测试和平台处理，不受原目录结构或原七个主题约束。

不能因为找到一个函数就停止：需要理解它的调用前提、实际副作用和结果反馈，
避免把局部能力当成完整链路，也避免将业务耦合藏在可复用函数后面。

旧项目没有对应实现也是有效结论；明确说明即可，不伪造可复用能力，
也不要求在提取任务中补建它。

## 四、怎样判断是否有用

### 可以提取的内容形式

由发现决定，可以是基础资料、视觉素材、小函数思路、局部执行流程、接口组织经验、
平台现象、故障教训或有价值的验证案例，不要求属于任何预设技术分类。

每项应能说明与本项目需求的关系及实际收益。
数量、文件数和提取比例不是目标；没有用处的不保存，已有的准确资料不重复抄写。

### 业务行为与技术方法分别判断

旧行为与当前需求不同，不代表附近代码完全没有技术价值。
需要辨别：

- 可独立借鉴的技术点是什么？
- 它依赖哪些旧模型、假设或副作用？
- 能否剥离这些依赖，仍留下有用参考？

不能只因某个模块带有旧架构就整块跳过，也不能把整块模块换个标题搬进来。
当前不采用某方案，不妨碍理解它的局部经验；但不能借提取擅自改变本项目的技术基线或产品行为。

当前“暂不做”不是永久技术禁令。提取中发现值得重新讨论的能力或方案，可以记录需求关联、
具体收益与代价，留给用户裁决；未经裁决不标成已确认要求，也不进入本轮产品实现。

### 对新增复杂度的判断

涉及额外检查、防护、恢复、抽象和特殊分支时，说明它防止的具体后果与价值。
旧代码存在、旧测试要求、“更健壮”或理论正确，本身不构成采用理由。
可接受、影响有限的后果不要求消除。技术资料可以记录取舍，不强制复刻旧机制。

## 五、交付资料应说明什么

每项保留内容用自己的话写清楚：

1. **需求关联**：引用本项目章节、FR 编号或最新明确要求，说明解决的问题。
2. **实际证据**：旧源文件、函数／组件和核查行号或提交，区分源码事实、注释、测试预期与本次推断。
3. **可借鉴内容**：让读者无需通读旧模块也能理解技术点，不只留一个源码地址。
4. **适用前提与局限**：包含必要依赖、耦合、旧行为及与本项目的冲突。
5. **验证状态**：静态核对、数据解析、隔离样例或未验证，不能冒充实测成功。

文档形式与主题划分按内容组织，不要求每项新建文件，也不要求每项机械套五个标题。
有价值的原始素材可保存到现有 assets，保留来源和许可。
必要的小示例可以保存，但不复制数千行模块，不将参考片段冒充已集成的生产实现。

第三方协议和目录是有版本的观察：未核对当前实际安装或当前一手实现时，明确保留为历史线索。
旧材料写“已验证”不表示本次也完成了验证。

## 六、执行边界

### 输出位置

主要完善 `docs/technical-reference/` 中已有文档、数据、素材与索引。
发现独立新主题且值得保留时，可以新增资料；不要求塞进现有分类。

主 Agent 先协调写入范围，避免子代理相互覆盖文件。
共享索引、跨主题合并和最终审查报告由主 Agent 统一处理。
为修正资料引用，可以小范围更新项目 README、需求文档的资料入口或视觉说明的素材链接，
不改变其中的业务结论。

### 本任务不执行的工作

- 不修改旧仓库、实际 SkillManagerVault、已安装 Agent 或工具文件。
- 不修改产品源码、HTML 原型、宪章、业务规格、依赖清单或部署配置。
- 不初始化应用工程，不执行真实安装、同步、部署或更新。
- 不恢复已删除的旧参考包，不创建旧工程镜像或整套旧测试副本。
- 不把技术发现直接变成已批准的新需求；需裁决的问题写进交接报告。

验证以读取源码、解析数据、核对素材和文档链接为主。
如确有必要做技术试验，只用自己的隔离临时目录与合成资料，不触碰真实环境。
不为形式完成而运行全部旧测试；同样不能以“只做参考”为由伪造运行结论。

## 七、执行方主 Agent 审查

子代理交付后，主 Agent 必须实际审查并整合：

- 回到需求覆盖表，检查是否遗漏功能、共享约束、跨功能链路或已知痛点。
- 每项保留内容是否确有用途与证据；对关键或有争议的结论亲自核查源码。
- 是否存在因旧行为不符而错过可剥离技术的情况，或因技术可用而把旧行为一起搬入的情况。
- 从最终资料中移除不需要的旧裁决、隐含业务假设和与当前要求冲突的行为。
- 合并重复内容、消除跨代理矛盾，保持一套技术索引、数据和素材。
- 核对实际 JSON、数量、素材映射、许可和本次相关文档链接。
- 核对写入范围，确认未改原型／业务规则、未触碰真实环境、未恢复旧资料文件夹。

对于不能确定是否有价值或是否与需求冲突的部分，明确列出问题和影响，交给后续复查。
不能为获得“全部通过”而隐去疑点，也不能只收齐报告就声称完成主 Agent 审查。

## 八、统一交接报告

主 Agent 生成 `docs/technical-reference/extraction-review.md`，与技术资料一起交付。
不需要每个子代理单独保留一套永久报告，也不另外复制“最终版”目录。

报告至少包括：

- 实际源版本／提交、检查范围与验证边界。
- 至少五个实际子代理的标识／任务名、职责和交付。
- 需求覆盖表的最终结果；没有可复用实现、未覆盖或需补查的地方如实标明。
- 新增／修改／删除的文件及主要内容。
- 发现的旧行为、与哪项需求冲突、如何从提取成果中剥离或移除。
- 主 Agent 亲自核查的关键来源、纠正的问题与数据／链接检查结果。
- 供签发方复查的疑点、尚未验证的外部事实、建议用户进一步裁决的事项。

报告重点回答“按需求发现了什么、为什么有用、没有带入哪些旧行为、还不能确定什么”，
不复制工具日志或流水账。

## 九、完成与回交

完成条件：

- 需求清单驱动检查，主要需求及共享约束都有覆盖交代，不要求每个需求都产生新资料。
- 至少五个子代理实际参与，主 Agent 已审查、整合并修正成果。
- 技术参考有实际用途、独立可读、来源可查，旧行为与新需求清楚分开。
- 有用的新发现不受预设主题限制，资料结构也不被原七组分工固定。
- 索引与统一交接报告已完成，未越界执行产品开发或真实维护。

向用户给出技术索引与交接报告的绝对路径，并说明实际完成的审查及限制。
由用户将结果交回签发方 Agent；不要自行向其他聊天发送消息。
执行方完成的是提取与首轮主审，不声称已获得签发方验收。
签发方随后再结合实际文件做第二轮复查，继续删除不适用的旧行为。
