# Git 获取与仓库 Skill 发现

2026-10-15 对 FeiSkillDock v1.44.0 源码的第二轮静态检查。
没有运行下载、验证认证或重现大仓库失败；以下是技术参考，不是现有故障的根因结论。

## 获取进度：值得保留的部分

参考实现用系统 Git 的 `--progress` 将进度送入 stderr，独立读取线程向调用者传递文本。
读取器同时按 `\r` 和 `\n` 分割，因为终端进度经常在同一行刷新；仅等待换行可能看不到及时变化。
前端在发起请求前订阅进度事件，并按本次任务标识过滤，避免其他任务的消息混入。

取消路径检查取消标记，结束子进程并等待退出；需要核对实际下载、检出等耗时阶段是否都能取消。
最终成功以退出状态和操作结果为准，不能将进度中的百分比或阶段结束直接当成入库成功。
进度百分比只描述其所属阶段，不伪装成整个任务的统一百分比。

静态检查证实：`preview_git_install` 已连接进度回调和取消注册，来源文档／差异预览的部分获取调用
却没有传入进度和取消参数。因此“旧版从未实现进度”不准确；具体用户操作在哪条链路缺少可见反馈
仍需复现。已有回调也不证明界面反馈足够清楚。

## 不直接继承的获取机制

- 旧获取器多处使用固定 300 秒超时。对大仓库可能不合适，但不能据此宣称它就是此前失败的根因。
- 旧版同时包含系统 Git、`git2` 回退、稀疏检出、缓存锁与淘汰、代理等机制。
  当前本项目使用本机 Git，不为复用获取代码而带入整套引擎或回退体系。
- 缓存命中后仍可能有网络和检出工作；不把“已下载”当作以后阶段必然立即完成。
- `resolve_remote_revision_with_git` 的远端查询通过阻塞 `output()` 执行，不能假定它已经获得
  克隆循环中的超时和取消能力。实施时关注用户实际等待的完整路径。

这些观察用于选择小范围实现或验证场景，不要求先实现通用下载框架。
认证仍遵循本项目已有要求，复用本机 Git 配置，不沿用旧专用凭据系统。

## 仓库内容识别

旧代码把“确定扫描容器”和“枚举实际技能目录”分开：仓库根本身可能是一个 Skill，
也可能只是包含 `skills/`、`skill/` 或其他嵌套目录的集合。
预览输出实际技能及其仓库内相对位置，再由用户选择；容器本身不能因为名字匹配就被当成 Skill。

可借鉴的具体做法：

- 入口标记文件的读取、合法性检查及后续内容处理采用一致候选顺序。
  旧版记录 `SKILL.md` 与 `skill.md`；新项目支持何种输入以自身规则确定。
- 在目录里找到实际技能后停止向其内部递归，避免误把 `references/` 等内容当成独立技能。
- 排除 `.git`、`node_modules` 等无关扫描范围，并关注链接循环导致扫描无法结束的实际后果。
- 预览条目携带仓库内相对路径，不能只用末级名称标识不同目录的候选；跨平台展示统一使用 `/`。
- 用户明确选择的路径不存在或不是技能时，不能退回仓库根安装，否则可能把整个技能集合错误复制进去。

旧分类派生方式不直接复用：当前多 Skill 仓库默认分类按仓库名、允许修改。
旧自动生成目录后缀和 `sanitize_name` 静默改名也不带入，当前同库重名规则是提示并阻止。
旧解析器存在将读取／解析失败折叠为“没有元数据”的路径，不能据此声称错误已经被明确反馈。

## 按需验证的具体场景

单技能仓库、多技能嵌套仓库、相同末级名称位于不同路径、选定路径无效、进度只有回车、
大仓库长时间获取、网络失败、用户取消。验证观察候选范围、等待反馈、退出结果和库内实际变化，
不直接继承旧测试集数量或断言。
