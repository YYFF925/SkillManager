# 故障诊断与文档阅读参考

本页记录第二轮源码检查发现的可复用技术点，不引入旧工具中心的数据模型或通用治理机制。

## 结构化结果与错误信息

旧前后端通过结构化错误的类别与中文消息提供可读失败信息，普通失败不只抛一个对象给界面。
可借鉴的是“保留可供机器判断的原因，同时让用户读懂失败”的做法，
而不是复制旧错误枚举、所有权策略、冲突 payload 或各层适配器。

同一批任务中，可以保留每项的目标、成功结果与失败原因。
例如旧 Agent 指令分发的 `InstructionsOutcome` 记录目标 key、路径、写入字节及错误，
使一个目标写入失败不被其他目标成功掩盖。CLI 与 GUI 对同一结果不能各自宣称不同的成功状态。
具体字段与批处理方式由本项目实际接口设计确定。

## 诊断内容中有用的范围

旧实现已有当前版本／平台资料、最近日志摘录、崩溃线索、连续重复日志合并与日志导出。
其中可参考的重点是：保留出错操作、真实失败原因及相关环境，使用户能将问题交给 Agent 排查。
不带入旧审计数据库、历史恢复、固定日志 ZIP 格式或全部保留策略。

日志中可能出现带用户信息的路径，以及带凭据的远端 URL。
旧 `log_sanitize::sanitize` 对 home 路径、URL userinfo、部分 token 前缀和邮箱作替换，
诊断导出也会调用它。这能减少用户分享排障资料时把真实凭据一起复制出去的具体后果。
旧正则只覆盖部分形态，不证明所有敏感内容都已识别，也不作为新的完整凭据检测引擎。

错误文本与脱敏后的展示不要覆盖原始业务状态；日志可读也不代表操作已被修复。

## Markdown 阅读的小范围复用点

旧页面使用 `react-markdown` 与 `remark-gfm` 阅读 Markdown，并为代码块提供复制操作。
这符合本项目正文、中文阅读译文、工具简介和维护指南的展示需要；不用自写完整 Markdown 解析器。
这只是沿用已选前端体系中的技术线索，不冻结当前依赖精确版本。

值得保留的职责分离：

- 文档中的文本与 HTML 片段作为阅读内容，不能因打开维护文档就执行其中的脚本。
- 外链交给系统打开，不将桌面应用本身导航离开；链接点击不代表执行安装命令。
- 相对图片按当前文档资料目录解析，不允许任意文档引用替代应用对整个本机文件的访问授权。
  否则来源不受控的文档可能借图片位置读取并展示用户未选择的本机内容。

旧 `resolveDocImage` 的根目录硬编码为工具中心的 `root/tools/<name>`，
不能直接作为技能正文、嵌套 references 文档或 Windows 路径的通用解析器。
旧 DTO、文档文件名约定、必填文件组合及 Tool Center 状态派生不一起继承。

## 来源定位

- `src-tauri/src/core/error.rs`、`src/lib/error.ts`：结构化错误与消息提取。
- `src-tauri/src/commands/settings.rs`、`src-tauri/src/core/panic_log.rs`：诊断与崩溃记录。
- `src-tauri/src/core/log_sanitize.rs`：展示／导出前的日志内容替换。
- `src/tool-center/components/SafeMarkdown.tsx` 及相邻测试：Markdown、外链、图片和复制。
