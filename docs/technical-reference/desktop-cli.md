# 桌面与 CLI 平台工程参考

正式技术栈见[项目原则](../../.specify/memory/constitution.md)。
此处只记录旧实现遇到的具体平台现象，不引入既定发布流水线或旧工程门禁。

## CLI 需要可发现的入口

Tauri 桌面包中有 CLI 二进制，不代表外部 Agent 的进程能从 PATH 找到它。
实现分发时需确认从普通终端及 Agent 实际进程能调用同一版本的 CLI，
并在维护 Skill 中说明调用方式；不能用“GUI 内能运行”代替外部可用性的证据。

旧实现通过固定路径副本、版本戳及桥接函数解决这个问题，但这些不是本项目已选方案。
目录、链接还是副本、发布方式等，按实际打包结果选最小方案。

## 平台现象与核查线索

| 环境 | 旧实现遇到的现象 | 实施时的关注点 |
|---|---|---|
| macOS | 应用可启动，包内 CLI 仍可能受签名／隔离属性影响而不能由外部进程调用 | 验证实际打包产物中的 CLI，不把开发目录可运行等同于发行可用 |
| Windows | GUI 拉起控制台程序出现黑色控制台窗口 | 检查启动参数与结果可见性，避免窗口闪烁或隐藏执行失败 |
| Linux AppImage／移动应用包 | 直接指向临时挂载或旧位置的链接失效 | 确认维护 Skill 记录的入口在真实分发方式下可用 |
| 非交互 shell | 开发者终端加载了环境初始化，Agent 或构建进程没有加载 | 验证实际进程的可执行入口，不将个人 shell 配置写成通用前提 |

这些现象是历史记录，不代表当前必然复现，也不授权直接照搬旧桥接、自动删隔离属性或恢复链。

## 验证按实际结果组织

- 分别从 GUI 与外部 CLI 执行同一项核心管理任务，检查业务结果一致。
- 发布核查选择项目实际支持和交付的平台，不继承旧 CI 的 runner 矩阵或未运行平台的成功宣称。
- 文件／配置／部署相关检查可使用隔离样例，避免为了验证而改动用户的真实技能和工具。
- 测试数量、文件组织、禁止 mock 的旧规则、版本号联动九文件等，不作为新项目门禁。
