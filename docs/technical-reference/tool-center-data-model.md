## 简介与维护指南的内容骨架

旧 `overview.md` 回答：工具是什么、为什么纳入、给 Agent 增加什么能力、典型场景及边界。
这正好服务用户“时间久了不知道装过什么工具”的问题，不能用一句卡片摘要代替。

旧 `operations.md` 提供以下研究问题，按当前工具取有用的内容即可：

- 如何调用；支持的平台与前置条件。
- 安装方式、安装位置、配置位置，如何判断已经安装。
- 如何获取本机版本与上游版本，依据什么来源。
- 如何安装、更新、卸载；执行后如何验证，已知注意事项。

旧研究指南列举 registry（软件包登记源）、Release（发布版本）、Git tag（标签）、
commit（提交）等版本来源。这是识别检查方式的线索，**不冻结统一优先级**，也不要求第一版全部接入。
新项目实际支持哪些来源及如何登记检查方式，仍待设计。

简介供人阅读，维护指南供 Agent 执行维护时参考；两份资料可分别展示。
不由此恢复旧 `history.md`、巡检日报或多电脑健康监控。

## 版本检查的职责不能照搬

旧 `computeDerived`（`src/tool-center/data/derived.ts:103-126`）的 `hasUpdate` 只是
“任一已部署机器的 `update` 等于 `available`”，没有获取上游或比较版本。
旧 `state.yaml` 中安装版本、更新状态由外部 Agent 填写。

因此旧更新徽标只能参考呈现，不能当成软件已完成检查的证据。
新链路需要区分本机安装记录、软件实际获取的上游版本及检查结果；
“尚未检查”“检查失败”“已检查且最新”不能混同。
工具本体仓库地址也不能自动等同版本检查来源，例如通过包管理器安装的工具可能按包版本查询。

检查由软件执行，安装与升级由外部 Agent 按维护指南处理，任务完成后回写真实安装结果。
这些职责已确认；本文不新增自动安装器、后台 Agent 或通用命令执行引擎。

## 配套技能关联

旧 `skill` 资料能表达“有技能、是否官方、研究摘要”等信息，但没有库内技能关联。
本项目需展示具体技能候选、来源与入库状态，让用户选择目标库并补充中文注释、标签、分类等资料。
多技能来源复用已有仓库预览选择流程；入库不自动部署到 Agent 或 Hermes 档案。

工具版本与配套技能上游版本各自处理，不能因工具更新就宣称配套技能已更新或反过来。
这不要求复制一份技能正文进工具中心，技能维护仍在 SkillManagerVault。

## 文件读取、错误与界面可借鉴点

旧后端 `tool_center/scan.rs` 枚举工具目录，返回文件存在信息与读取错误，正文由
`doc.rs` 按需加载。可参考：

- 清单不加载全部长文，打开详情后再读取简介/指南。
- 单条工具资料损坏时标出该条错误，其余工具仍可浏览，避免一条坏资料遮住整个清单。
- 错误包含可定位的文件与原因，便于 Agent 修复；旧 `error.rs` 的具体枚举不继承。
- 文档相对路径应限制在所选工具资料范围内，防止点开附图或文档时读到无关文件；
  具体路径处理参见[诊断与阅读参考](diagnostics-and-documents.md)。

旧文档名白名单只适用于旧工具资料的固定文件集合，**不能推广为技能文件只允许固定 `.md` 名称**；
技能详情需要读取内部层级文件。路径范围与文件名白名单是不同限制。

旧 malformed 样例体现“单条解析错误隔离”；未运行这些测试。
`schema_version == 1` 的旧校验不是版本迁移本身；不继承的原因是新格式尚未确定且不兼容旧数据，
不能据此宣称新项目永远不需要格式版本或必需字段校验。

## 架构与存储边界

旧软件 Rust 侧只提供扫描与读取原文，YAML 解析及更新状态派生在 TypeScript 前端。
这是旧只读面板的结构，**不是新项目建议架构**。
本项目已确定 GUI 与 CLI 共享 Rust 业务核心；版本检查、状态判定及资料业务规则应遵循该原则，
避免 CLI 为复用规则而依赖前端解析器。

旧 `config.yaml.machines`、`state.yaml.machines`、健康聚合、过期巡检阈值、归档与历史模型
不进入当前参考契约；旧 `TOOL_CENTER_HOME` 定位及旧目录迁移也不继承。
工具资料是否跨电脑同步、具体存储位置、Agent 回写格式与检查来源范围，
需求仍未确定。不能因为旧代码是本地文件就替用户定为“所有工具资料只存本机”。
