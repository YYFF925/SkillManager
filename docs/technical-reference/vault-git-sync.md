## 先区分旧来源库与自己的库同步

旧 `core/skill_vault.rs` 把 SkillManagerVault 当作外部来源，再导入另一个中央库。
它的 fresh/existing/conflict/removed 名单不能直接用作新项目自己的跨机同步。

新 SkillManagerVault 就是用户维护的唯一库根，含 code/lobster、管理资料、预设和指令源。
各电脑的部署记录、Hermes 启用选择、指令分发目标与上传确认状态留本机。
旧较接近的实现线索是 `git_backup.rs`、`auto_backup.rs` 及其调用方。

## 同步触发与上传：旧链路的限制

旧 `file_watcher.rs:361-362` 发现库变化就通知自动备份。
`auto_backup.rs` 使用 120 秒尾随防抖、15 秒检查循环，启动首次延迟 90 秒；
`run_round_blocking:200` 在开关开启、本地 Git 仓库和远端存在等前提下执行：

```text
获取远端状态 → 写旧镜像 → 提交本地变化
→ 必要时合并远端（旧默认对象引擎）→ 必要时推送
```

这些步骤有锁占用、远端状态、网络失败等退出条件，**不是任何文件变化后必然两分钟上传成功**。
但代码没有区分 GUI 与 Agent 改动，也没有用户上传同意判断，因此确实可能上传未经同意的 Agent 改动。
旧系统 Git 合并分支在后台遇远端领先会等手动同步，与默认对象引擎行为还不同。

旧手动 `run_sync_blocking`（`commands/git_backup.rs:447`）也是提交、合并、快照、推送的组合，
不能直接接到新项目“主动同步主要拉取”的按钮。

| 本项目已确认 | 旧实现差距 |
|---|---|
| 启动、定时、手动拉取，无冲突静默应用 | 旧变化防抖不是远端定时检查；不能因本地无变化就不检查远端 |
| 默认 1 小时，可关、30 分钟、6 小时、24 小时 | 旧自动备份主要是开关与固定防抖，没有这组周期设置 |
| GUI 保存按已确认规则上传；Agent 每次维护后先询问 | 旧任意库变化进入自动上传，无法区分尚未授权的改动 |
| 后台、主动同步、重试不能顺带上传未同意的改动 | 旧 `push` 推送分支提交，没有改动授权边界 |
| 拉取后同步本机已有部署，新技能不首次部署 | 不能用重建列表/索引代替更新部署，见下节 |

旧提交与推送分别有函数入口（`commit_all_unlocked`、`push_unlocked`），可参考职责分离。
**这不表示 Agent 可在未同意时先自动提交**：当前需求是得到同意后才提交推送。
如何记录并限制已获同意的上传范围是实现设计，不能在此擅自引入快照、授权账本或多分支流程。

## 同步后的部署刷新：复核后的准确范围

在以下已读调用链中，合并后调用 `reconcile_skills_index_unlocked`
（`commands/git_backup.rs:393/485/1195`；`auto_backup.rs:277`），主要重建索引。
`core/merge` 未直接调用部署；`Backup.tsx` 刷新列表与预设。
文件监听后，`AppContext.tsx:373-412` 先刷新管理索引再刷新界面数据；
`refresh_manager_index_internal`（`commands/skills.rs:415`）本身不写部署。
这些观察支持“已查同步回调未直接刷新副本”，**不能证明旧程序所有路径都不会刷新部署**。

第二轮还发现启动确有部署路径：`core/app_state.rs:121` 在 GUI 启动条件下调用
`ensure_default_startup_scenario`，该函数再调用 `sync_scenario_skills`
（`scenario_service.rs:1126-1173`）。它依赖旧互斥预设，不能用于新项目，
也不能继续把“旧程序不会自动刷新部署”写成绝对结论。

可评估的小原语是 `resync_copy_targets`（`commands/skills.rs:3946`）：遍历已登记副本，
重新复制/合成并更新记录。但它不等于新需求完整链路，旧内容变更检测也没有在所有写前接入。
本项目要连接“库变化 → 本机已有部署重合成”，并按已确认规则暂停有本地变更的副本；
连接在哪个服务是后续实现选择，不要求用户先裁决函数结构。

## 冲突处理可以借鉴什么

旧默认对象引擎以技能 ID 与分量做三方比较，另有隐藏 Git 引用、提交 trailer（尾注）、
待裁决数据库投影及“保留本地/远端/双方”界面。
它还会按时间覆盖部分元数据、给路径碰撞自动加后缀。这些规则都不能变成新项目的冲突规则。

旧系统 Git 路径 `merge_branch_system`（`git_backup.rs:749`）遇合并失败会尝试 abort（中止合并）
并返回 `SYNC_CONFLICT`。可借鉴的是让失败可见、交给 Agent 检查，而非沿用重新克隆引导。

新需求已确定冲突时暂停本次同步、Agent 检查、用户裁决，无专用裁决界面。
**尚未确定冲突现场如何保留或中止**，不能把旧 abort 或任意 checkout（检出覆盖）写成新恢复流程。
系统 Git 可自动合并的改动与需用户处理的冲突也应区分；
“不提供冲突界面”不等于“不允许 Git 自动合并无冲突改动”。

## 本机并发与单文件写入经验

旧 GUI 与每次 CLI 调用是不同进程。`RepoLock`（`repo_lock.rs:16,56,91,111`）使用文件锁
串行化同机仓库写操作，防止两次提交/文件移动互相干扰。
这只约束使用同一锁的程序，不约束直接修改文件的外部 Agent，也不能解决跨电脑并发。

锁文件旧放 base_dir 外层，是为避免旧整库改名时 Windows 占用问题。
本项目不因此继承旧位置、20 秒等待或重新克隆流程。
若实现出现 GUI/CLI 重叠写同一库的实际问题，可参考这一小技术点，范围应由具体写操作决定。

`sync_metadata::atomic_write_bytes`（`:1034`）使用同目录临时文件、写完后 rename（改名替换），
避免一次中断留下半个元数据文件；它不提供多文件同步事务。
旧清理临时文件、拒绝不完整镜像和旧格式门控还绑定专用合并引擎，不能作为一套必需防护搬入。
详见[内容合成参考](content-composition.md)。

## Git 状态、认证与容量报告

旧 `get_status` 读取 ahead/behind（本地领先/落后提交数）与远端状态；
`auto_update_last_run_at` 是技能上游检查时间，不能当作 SkillManagerVault 上次同步时间。
旧未提供完整持久化的库同步时间/结果记录；需要何种界面状态按新需求设计。

本项目复用已有仓库的远端、分支、作者及本机 Git 认证。
旧改写作者、专用 keychain（系统钥匙串）、GitHub 授权、凭据迁移、另存远端配置、
git2 与合并引擎切换均不继承。提交/推送命令仍需遵守前述上传同意边界。

旧 `size_report`（`git_backup.rs:1257`）只读扫描库文件，排除 `.git`，技能目录命中后不重复下钻。
这是容量报告的有用小实现点；旧只测 Code 根，新项目口径应覆盖整个 SkillManagerVault。
旧 100 MiB 单技能与 1 GiB 全库阈值只是历史取值，不是新要求。
旧自动写 `.gitignore` 排除大技能，会使技能无法跨机同步；
保留容量显示**不等于授权继承自动排除**，当前不把它作为实现要求。

## 不继承与尚待设计

不继承独立备份仓库、快照/历史恢复界面、重新克隆、断开远端、设备名称、
旧镜像与数据库迁移、对象合并协议及隐藏引用清理。
保留小技术线索不表示接纳整块模块；当前不采用也不构成永久禁令。

两种检查是否共用周期配置、已有需求中手动备份点的去留仍未确认，
不影响本次技术参考整理。同步与上传的具体实现按正式设计再确定，不能从旧代码倒推需求。
外部 Git 行为未进行实测，旧调用链的观察不等于本项目功能已经实现。
