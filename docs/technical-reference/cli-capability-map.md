## 机器可读结果与退出状态

旧 `main`（`skills-manager-cli.rs:1166-1201`）在 clap 解析前检查 JSON 输出开关，
让参数解析失败也能返回结构化结果。运行失败返回非零退出码。
`error_envelope`（`:4652-4677`）保留错误类型和结构化细节，避免 Agent 只能猜一句错误文案。

可参考的是这几个需求相关经验：

- Agent 能区分成功、失败及部分完成，并知道哪些技能/目标未完成。
- 错误带可判定类别与具体路径，普通文本与结构化输出含义一致。
- 批量中“拒绝/跳过”若作为正常结果返回，必须明确状态，不能只看进程退出成功就推断全部完成。
- 参数错误同样可以机器读取，避免只对业务错误提供结构化输出。

旧成功/失败的字段与输出方式并不完全统一：读命令常输出 JSON，部分写命令仍打印文本。
因此不能把“有 JSON 开关”写成全命令已经提供一致契约。新格式和退出码细分留到实现设计。

## 可选 dry-run（模拟执行）

需求已经确认：预演可报告将部署/撤销的技能、涉及 Agent 和目标路径，不实际改文件；
**不是每次操作前的强制步骤**。不新增强制预演或额外确认流程。

旧 `run_skill_deployment` 在 dry-run 分支跳过写部署与日志，只算技能/Agent 对及阻止项
（`:2049-2103`）；报告缺目标路径。旧 `preview_scenario_sync` 刻意不调用会删除失效部署的清理函数
（`scenario_service.rs:455-458`），说明预览不能复用含写副作用的查询。

这个局部分支只读不等于整个 CLI 启动绝对无写入；旧 CLI 还会初始化本机状态、重建索引。
实现新预演时需核对完整调用链，不把旧局部观察写成端到端保证。

旧删除分支要求确认参数，但旧 dry-run 并非所有破坏性操作的强制步骤。
原提取稿“强制 dry-run + yes”的建议已删除。

## 让外部 Agent 找到正确 CLI

外部 Agent 的 PATH（程序搜索路径）不一定包含应用打包的命令行程序。
旧 `cli_bridge.rs` 将随应用的二进制复制到固定路径并核对版本，用于处理此问题；
它也带来复制、版本戳、macOS 隔离属性与 Windows 启动处理，不能直接选作新方案。
详见[平台工程参考](desktop-cli.md)。

旧 `--skills-root` 不只是指定文件目录，还把数据库、日志、缓存切到按根路径隔离的命名空间
（`apply_root_overrides:1203-1237`）。本项目当前只管理一个库，不能因参考此开关就引入临时多库模式。
Agent 如何读取当前配置的库根是技术入口设计，不需要重做多库产品讨论。

分类交互应支持 Agent 先在对话中询问用户、再把确定值传给命令，不能强迫无人值守进程等待终端输入。
参数形式留待设计，不在此冻结。

## 管理 Skill 与 CLI 同步维护

旧仓库 `AGENTS.md` 记录过双域改造后示例漏传 domain 导致实际执行失败。
这说明配套技能与命令实现需要随开发一起更新，不能只改程序。

新项目已确认管理 Skill 是 SkillVault 中的普通技能，开发时维护入库。
不增加专用自动分发、升级、安装引导或专用冲突机制。
