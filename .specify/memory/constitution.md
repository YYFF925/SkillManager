# Skill Manager Constitution

## Core Principles

### I. 用户对能力的掌控优先

产品必须让用户理解自己拥有的技能与工具、用途、使用位置及操作结果，
并能按需要维护和调整使用状态。信息展示必须区分已知事实、待确认状态和执行结果，
不能将未检查、检查失败或任务已生成表达为实际操作成功。

自动化必须尊重用户指令，清楚表达执行范围和影响，不得通过隐藏行为削弱掌控感。
这不意味着每个动作都增加审批；具体自动化与确认规则由业务规格明确。

### II. SkillManagerVault 是统一维护中心

技能内容和个人维护成果必须围绕用户自己的 SkillManagerVault 统一管理，
支持多电脑持续维护和使用，不得另建需要用户重复维护的中央技能内容。
技能资产必须能够由用户与 Agent（代理）直接读取和维护。

共享资产与各电脑的安装、部署和使用状态必须分开，不能把另一台电脑的状态
当作本机已完成的操作。具体同步范围和记录形式由相应业务规格确定。

### III. 个人管理能力与技能内容可以持续维护

中文正文与注释、分类、标签、支持声明及目标适配是项目的核心管理能力，
必须同时服务自建技能与引入的外部技能。
个人管理资料和适配内容必须具有清楚的职责，能够独立理解并持续维护。

产品必须支持用户和 Agent 对这些内容反复调整，不能将其限定为入库时的一次性填写。
具体目录、字段、存储格式和适配合成方式由规格与设计决定，不在原则中固定。

### IV. 个人维护成果与上游更新能力共存

引入外部技能必须保留后续识别来源和获取更新的能力，
个人维护不能以切断上游更新为代价。
更新过程必须让用户理解外部变化及其对当前成果的影响，
不得不加说明地丢弃、覆盖或混淆个人维护成果。

来源更新与自己的 SkillManagerVault 同步必须有清楚的语义和结果边界。
这不要求所有本地字段永远优先；取舍、覆盖和确认规则必须由明确的业务规格表达，
不能由实现隐式决定。

### V. 人工操作与 Agent 维护遵循同一套规则

核心管理能力必须同时服务 GUI（图形界面）用户与外部 Agent，
并通过 CLI（命令行接口）支持 Agent 完成核心管理任务。
不同入口必须遵循相同的业务规则，不能形成互相绕过约束的两套管理体系。

配套维护 Skill（技能）必须与软件管理能力一起维护，
说明正确的操作方式及边界，使 Agent 能在明确指令下完成工作。
功能交付必须同时考虑人工使用与 Agent 维护的完整业务路径。

### VI. 以实际需要和实际后果控制复杂度

必须采用满足当前目标的最小充分方案。新增抽象、检查、防护、回退、恢复或特殊分支前，
必须说明它防止的具体后果，以及为何该后果不可接受。
仅凭理论风险、形式正确或“更健壮”不足以增加机制。
对后果可接受、影响有限且容易处理的情形，允许用户承担合理操作责任。

成熟且持续维护的库能够降低复杂度、提升可靠性时，必须优先评估复用，
不得无故重复实现已有能力。不能为绕开临时裁决而引入更复杂的方案。
信息或能力不足必须明确说明，不得静默降级或把推断写成事实。

### VII. 个人自用，不为多用户设计

本项目由同一人维护并使用。产品、规格与实现必须按单一操作者设计。
不得引入多用户账号、角色权限、租户隔离，也不得引入人与人之间的共享或协作能力。
不得为“适应不同类型用户”增加可配置项、引导流程或兼容分支。

同一人使用多台电脑、经统一入口远程管理本机，属于该操作者的多设备场景，不是多用户。
不得把多设备做成多人产品。

单一操作者的使用体验必须作为设计约束：减少无谓确认与重复手续，
结果必须可理解，失败必须说清。不得以“只有一个人用”为由降低界面与操作质量，
也不得以“以后可能有其他用户”为由扩大范围。

登录与访问控制可以存在，目的是保护这一名操作者的环境，不是建设用户体系。
具体认证方式由规格决定。

## 技术栈与架构基线

正式产品沿用原项目 FeiSkillDock 的技术栈体系，作为后续设计与开发的默认基线。
该选择用于保持开发体系一致和复用已有经验，不要求搬运旧代码、数据或全部依赖。

| 领域 | 确定的技术栈 | 职责 |
|---|---|---|
| 桌面应用 | Tauri 2 | 桌面容器、原生能力与前后端通信 |
| 前端 | React + TypeScript | 图形界面及类型化交互 |
| 前端构建 | Vite | 前端开发和构建 |
| 界面样式 | Tailwind CSS | 样式组织，沿用既有视觉体系 |
| 核心业务与本机能力 | Rust | 文件、仓库、部署及工具管理等业务执行 |
| 命令行 | Rust + clap | 面向 Agent 的管理入口 |
| 本机结构化存储 | SQLite，经 rusqlite 访问 | 本机状态及必要的索引或缓存 |
| 验证工具 | Vitest、React Testing Library、Rust 的 cargo test | 按变化影响验证前端交互与核心业务 |
| 依赖与构建工具 | npm、Cargo | 分别管理前端与 Rust 依赖及构建 |

GUI 与 CLI 必须复用 Rust 核心业务能力；前端负责交互和展示，
不能另行实现一套决定技能入库、更新与部署结果的业务逻辑。
共享技能内容与个人管理资料仍以 SkillManagerVault 中可直接维护的文件为资产来源，
SQLite 不能成为这些共享资产唯一且无法从库文件还原的存储。

技术栈声明不锁定全部依赖的精确版本，也不要求照搬旧版数据库表、状态管理方式、
Git 引擎或辅助库。具体依赖版本由实施时的兼容性、维护状态和实际需要确定，
功能取舍继续遵守已确认规格。界面原型使用的 HTML、模拟数据和浏览器存储
不改变正式产品的技术栈。

更换桌面框架、主要编程语言或核心业务组织方式属于技术基线调整，
必须说明实际收益、代价及对原则的影响，并与用户确认后修订本宪章。
基线内的常规依赖升级与辅助库选择属于实现工作，不要求逐项修宪。

## 需求与验证纪律

原则只记录长期价值、资产边界、管理规则和明确选择的技术基线。
具体业务行为写入 Spec（规格说明），交互、参数和算法写入相应需求或设计，
不得因其在某轮访谈中被确认就升格为永久原则。

必须围绕完整使用场景明确用户目标、决策、执行动作和可见结果。
尚不清楚的交互可以通过原型验证，用户反馈必须写回需求或设计；
必须区分已确认要求、待验证假设、模拟状态和真实能力。

实施前必须明确工作对应的规格与当前范围。验证与实际后果相称，
重点检查真实业务结果；不默认要求所有改动采用 TDD（测试驱动开发），
不为低影响、可逆改动增加仅复述实现的测试。
交付时必须说明结果、必要的验证证据及实际限制。

当前“暂不做”不构成永久禁令。后续发现实际需要时，必须说明场景和理由，
修订对应范围，而不是强行绕路。旧版实现用于参考，不能代替新产品的业务判断。

## Governance

本宪章是规格、计划和实现的长期治理依据。用户后续明确指令优先于既有文档；
发生冲突必须指出，并更新适当层级的记录，不能通过解释旧记录回避用户意图。

修订原则必须记录变更内容、依据及影响，并与用户确认。
符合原则的功能迭代、设计调整和常规实现选择按各自任务推进，
不得仅因宪章存在而增加重复审批。

版本采用语义化版本规则：不兼容的原则删除或重定义提升 MAJOR（主版本）；
新增原则或实质扩展治理提升 MINOR（次版本）；不改变含义的澄清与修正提升
PATCH（修订版本）。修订时更新日期，保留首次通过日期。

规格、计划与代码评审必须检查原则符合性，指出实际偏离及其后果，
不能为形式合规扩大范围。原则本身不再适用时，必须明确提出修订。
宪章更新流程只修改本文件；依赖文档在相应后续任务中读取和遵循宪章。
